下载测试

两个平台走的是完全不同的路,所以要分开看结果。

Android:原生 DownloadListener → 系统 DownloadManager。通知栏会出现下载进度,完成后能在「下载」里找到。 请求会带上 WebView 的 cookie(漏了这步,登录态文件会下成一个登录页 HTML, 而且 HTTP 200 看着还像成功)。

iOS:app-shell.js 拦下链接交给 Browser.open()(Safari View Controller),你在里面「存到文件」。 不走原生是因为拿不到 WKDownloadDelegate —— 要触发它必须先占住 navigationDelegate,而那个被 Capacitor 占着,硬抢会连带废掉离线页和 bridge 清理。
iOS 上有一个必须知道的限制。 Safari View Controller 不共享 WebView 的 cookie, 所以「需要登录才能下载」的文件在 iOS 上会失败(下到登录页)。 解法在服务器端:给下载链接发一个带签名的短期 URL。 这一页的文件不需要登录,所以测不出这个问题 —— 但你的真站上会遇到。

1. 带 download 属性的链接

最可靠的一种,两端都认。

2. 只靠扩展名认出来的链接

没有 download 属性,靠路径结尾的 .pdf 匹配上 app-shell.js 的 downloadExtensions。

3. 认不出来的那一类

路径里没有扩展名的导出接口(/export?type=pdf 这种)认不出来。 这不是 bug,是规则本身的边界 —— 真站上遇到就给那个 <a> 加 download 属性。下面这个链接故意不带扩展名,点了应该不会触发下载。

4. 外链分流

站外域名应该不在当前 WebView 里打开。 externalInAppBrowser: true 时走应用内浏览器(有「完成」按钮那种), 改成 false 就丢给系统浏览器。不管哪种,都不该把你挤出 app。
